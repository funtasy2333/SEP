# WP8：GB/T 46687.2—2026 XML 实施方案

决策日期：2026-10-05。状态：**方案已修订，代码尚未实施**。
本方案与 [Phase 5.5 主计划](dev-plan-phase-5.5.md)共同构成实施规格；XML相关内容以本方案为准。

## 1. 已确认的范围

XML只提供 **GB/T 46687.2—2026《标准机器语言表达 第2部分：基于XML的标准文档内容标记指南》** 的导入、导出。

- 完全切断GB/T 37967 XML及SEP早期自定义XML：无旧解析器、旧导出器、兼容开关、自动转换或独立迁移工具。
- 独立NISO STS渲染器、导入配置、导出菜单和符合性目标暂不开发。新国标使用的STS标签体系、TBX、MathML、XLink仍需实现。
- 本次更改XML交换格式，不删除数据库文档、历史版本或JSON正文。已有合法PM JSON经当前生产Schema正常打开、保存、复制及回滚。
- 仅有旧XML、没有可用JSON正文的记录不提供兼容读取/回滚；显示明确的不支持原因，保留原始记录。实施前只读盘点此类路径和数量，不批量删除或转换。
- 切换一次覆盖所有XML入口；用户界面最终只有“XML（GB/T 46687.2—2026）”。不得保留“37967兼容”“NISO STS·征求意见稿”等旧入口。

这里的格式切换是用户确认的产品选择，不表示37967标准已被废止。

### 1.1 编辑器范围边界（2026-10-05，用户确认）

SES现阶段负责内容编写、文档结构、格式检查、引用管理及GB/T 46687.2 XML导入导出。GB/T 46687.1—2025、GB/T 46687.3—2026暂作背景资料，不作为本阶段实施或符合性目标。

- WP6/WP8范围不扩大，不新增语义模型预留、技术指标抽取、对象/属性/关系建模、知识图谱、规则执行或检测结果判定任务。未来如有明确应用需求，另行评估和立项，不构成本阶段依赖或验收条件。
- 本方案的“语义检查/保真”指文档结构与XML字段含义，包括章条角色、日期、TBX/MathML、ID/引用及资源关联；这些检查和内容保真要求继续实施，不等同于技术要求的语义建模或符合性判定。
- 文档nodeId、导出xmlId及Resolver继续用于编辑器寻址和文档引用，不据此增加技术对象ID体系；第2部分需要的元数据和IR/生产Schema补齐要求继续实施。

## 3. 工作包分工与数据流

### 3.1 WP6：内部模型及JSON基础

负责JSON渲染迁移、IR/生产Schema补齐、PM↔IR适配、Resolver引用/ID和存储边界调查。
不负责保留或重建旧XML。不要求输出与旧XML golden字节一致。

| 当前基础表达 | WP6补齐要求 |
|---|---|
| 基础题名、单个编号字符串、日期 | 分段/多语种题名、编号组成、语言/发布机构/版权；与现有元数据建立明确优先级和一致性规则 |
| 固定中文/英文术语字段 | 多语言集、多术语组及描述符；保留定义、来源、领域、注、示例和术语引用 |
| `IRFormula.latex` | 增加原生MathML、行内公式、公式注；导入MathML不能强制有损反译成LaTeX |
| 基础表格与图资源字符串 | 单位、表注/脚注、必要样式/宽度、图组和说明；独立可序列化资源清单 |
| 文本及基础crossRef | 变量、完整样式、代码/引文/警告、类型化文献、外链、索引和明确引用目标 |

既有字段保留已用语义，新增结构与默认值进入类型和Schema测试；JSON新增字段明确版本/扩展契约。
新增信息须在编辑器保存、重开及各输出边界保持或明确报告，不允许Schema丢弃字段后仍宣称导入成功。

### 3.2 WP8：唯一XML格式

```text
导出：生产PM JSON → pmToIr → resolve → MathML/资源准备 → xml46687 → XML + 配套资源
导入：XML + 配套资源 → 解析/结构校验 → 纯数据树 → XML到IR → irToPm → Schema校验 → 保存
```

- `packages/shared/src/renderers/xml46687.ts`：纯函数，消费IR、Resolver标签和纯数据形式的已准备内容，输出XML字符串。
- `packages/shared/src/ir/irToPm.ts`：纯数据反向适配；XML中外部ID映射为稳定内部nodeId，重新导出按Resolver产生xmlId。
- `packages/shared/src/xml46687/`：元素数据模型、元素到IR映射、语义检查和问题类型。DOM、文件读取、DTD/XSD执行不在shared中。
- client XML适配层负责命名空间解析、生产Schema接入、文件/资源处理、公式转换及交互；server/未来CLI可使用自己的解析适配。
- 当前 `xmlSerializer.ts`、`xmlParser.ts` 的公共调用可暂保留薄壳，但内部只能指向新实现；旧算法、字段别名兼容及 fallback 必须删除。

### 4.1 公式边界

优先在client适配层复用现有KaTeX产生MathML，渲染器只消费转换结果；确认实际版本、转换覆盖范围和错误行为。
原生MathML导入要保存有效原文/结构，编辑器展示、保存、再次导出不可丢失；LaTeX只是可用的编辑源，不能成为唯一权威内容。
无法转换或无法被生产Schema保真的公式应返回含位置和原因的问题，不替换成图片、空公式或旧tex-math。
同步验证MathML与现有DOCX/HTML消费路径；不能为了新XML破坏现有文档输出。

### 4.2 资源交付

XML与图片等二进制资源一起交付：导出含资源时提供资源包（XML+清单+资源），纯文本文件可直接下载XML。
XML引用名称、物理文件名、格式和资源键通过清单显式对应，避免仅留下不可解析的dataURL或本机路径。
图引用遵循第8章名称约定；资源包解包后能在另一目录解析，资源名冲突及缺失必须报告。
导入支持新国标XML文件及其配套资源包；无资源的纯XML可单独导入，缺少必要资源时阻止替换当前文档。

## 6. 所有XML调用入口的切换

WP6盘点、WP8.4逐项清理，至少包括：

- `EditorView.vue` 的XML文件上传、导出卡片、源码格式切换、源码复制/下载。
- `serializer/index.ts` 等公共入口及所有 `serializeToXml/parseXmlToJson/parseXmlToEditorJson` 调用。
- `VersionPanel.vue` 的版本快照XML生成；快照XML失败时中止该次版本创建并说明原因，不吞掉错误后保存部分快照。普通正文JSON保存独立运行，不能因旧XML被切断而失败。
- 文档复制、元数据校准、版本预览/回滚/导出、服务端或客户端缓存XML的路径；回滚使用可用JSON正文，不调用旧XML解析器。
- 库中的XML样例和测试：旧样例只可作为“应拒绝”的负例保留，不作为新XML golden；历史验收记录不改写成新格式验收结果。
- README、源码说明、菜单标签及后续CLI/MCP的XML格式名。

格式判断不能只看 `.xml` 或 `standard` 根元素：旧标准和新标准都可能同名。真正37967的`content/edit/execute`
以及SEP旧自定义命名空间/标签组合应明确拒绝；新格式按确定的内容模型验证，不依赖文件自称合规。
解析和校验使用固定本地资源，不在导入时联网获取任意DOCTYPE或外部实体。
